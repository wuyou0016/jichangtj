## 先说结论

自测记录表的作用，是把“感觉不太好”变成“某个时段、某个节点反复出现某个问题”。表不用复杂，**每次用同样的方式填**，比列很多更重要。下面是一张够用的 7 列表，以及怎么读它。

## 7 列够用了

| 列 | 怎么填 | 为什么要 |
| --- | --- | --- |
| 时间 | 日期 + 星期 + 时间点，如“周三 21:00” | 看问题是否集中在同一时段 |
| 节点 | 地区 + 编号，如“香港 03” | 区分“个别节点”和“整体” |
| 测法 | ping / 客户端测试 / 应用内 | 不同测法数字不能混比，见[自己怎么测延迟](/knowledge/test-latency-methods/) |
| 数值范围 | 延迟最小到最大，丢包百分比 | 看波动，不只看平均 |
| 体验 | 一句话：流畅 / 偶尔卡 / 断线 | 数字之外的真实感受 |
| 对照 | 直连或另一条网络的结果（可选） | 判断是不是你自己网络的问题 |
| 备注 | 当时在做什么、有没有人同时下载 | 排除干扰因素 |

不需要加“评分”列。评分需要可比较的结构化数据，一个人一周的记录不足以支撑。

## 怎么填才有价值

- **延迟写范围，不写平均**：写“40–180ms”比写“90ms”有用得多；
- **体验用固定的几个词**：只用“流畅 / 偶尔卡 / 经常卡 / 断线”，避免每次用不同的措辞；
- **同一个节点反复测**：至少挑一个固定节点，每天在同一时段测，才能看趋势；
- **失败也要记**：连不上、超时同样是有效数据，不要只记成功的。

## 一周之后怎么读

1. **按时间筛选**：把所有“晚高峰”的行放在一起，看问题的频率；
2. **按节点筛选**：同一个节点的几天记录，看趋势是稳定还是变差；
3. **找“反复出现”的模式**：偶发一次的不算，同一时段每天都出现的才算；
4. **和对照列比较**：直连也有问题的，先排查自己的网络。

## 什么情况下可以提前结束

不一定要测满七天。出现下面任一种，可以提前做决定：

<ul class="checklist">
<li>连续三个晚高峰都出现明显断线，而且换了节点仍然如此（可以提前停止，直接换一家）</li>
<li>前几天晚高峰都稳定，且覆盖了你的主要用途（可以继续按计划，不必加测）</li>
<li>发现问题明显出在你自己的网络上（先修自己的网络，再重新测）</li>
</ul>

决定时要看套餐是否允许退款、是否是月付，见[月付还是年付：先看这四个问题](/knowledge/monthly-vs-yearly/)。
